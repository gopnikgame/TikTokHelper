# Размещение рядом с кабинетом VLine

Кабинет доступен по `/cabinet`, пульт по `/tiktokhelper/`. Каждое приложение устанавливается и обновляется из своего репозитория, со своей PostgreSQL и отдельными данными. Для TikTokHelper требуется отдельный запуск Compose из этого репозитория.

## Вход и доступ

Кнопка **TikTokHelper** появляется после входа в кабинет при `VLINE_TIKTOKHELPER_PATH=/tiktokhelper/`. Прямой вход в пульт без сессии ведёт к штатной форме кабинета. После входа кабинет возвращает пользователя в пульт. Ссылка **В кабинет** открывает текущую вкладку, во время подключения или эфира пульт предлагает соседнюю вкладку, чтобы сохранить работу со звуком.

Кабинет выдаёт одноразовый код на 60 секунд с PKCE S256. Пульт получает тот же UUID VLine, по которому уже хранятся роли и рабочие пространства. Доступ к LIVE проверяется существующим сервером подписок при входе и при каждом подключении к эфиру. После выхода или смены аккаунта в кабинете следующий запрос к пульту отклоняется. Открытый Socket.IO проверяет сессию перед командами и каждые 15 секунд.

Разрешения привязаны к конкретной сессии кабинета и хранятся в памяти процессов. Используйте по одному процессу BFF и TikTokHelper. После их перезапуска пользователь снова подтверждает вход через кабинет, сохранённые настройки остаются в базе. Основная cookie пульта действует в `/tiktokhelper/`. Отдельная `__Host-tiktok_helper_browser` защищает привязку к браузеру, поскольку другой поддомен не может её установить. nginx пропускает к пульту только эти две cookie. Браузерный origin общий, поэтому код обоих приложений и статические файлы на этом origin входят в одну границу доверия.

## Настройки оператора

На сервере кабинета задайте `VLINE_TIKTOKHELPER_PATH=/tiktokhelper/`, `VLINE_TIKTOKHELPER_CLIENT_ID` и `VLINE_TIKTOKHELPER_CLIENT_SECRET` через его действующий механизм серверных настроек. Для client ID допустимы ASCII-буквы, цифры и `._~-`, до 64 символов. Сгенерируйте отдельный случайный секрет длиной от 32 символов. Оставьте путь пустым, пока не готовы оба сервиса и прокси.

Чтобы выключить интеграцию в кабинете, уберите все три настройки. После применения конфигурации ссылка исчезнет, а пульт перестанет получать подтверждения сессий от кабинета.

Для TikTokHelper используйте обычный `compose.yaml` и подключите `deploy/cabinet.compose.yaml`. Этот профиль собирает web и запускает backend с одинаковым базовым путём. На одном хосте укажите свободный loopback-порт через `APP_BIND_PORT`. Используйте отдельную закрытую Docker-сеть между приложением TikTokHelper и BFF кабинета с постоянным DNS-именем BFF, указанным в URL обмена. Имя сети задаётся `CABINET_AUTH_NETWORK`. Присоедините только два приложения через их серверную конфигурацию, чтобы связь сохранилась после обновления контейнеров.

| Настройка TikTokHelper | Значение |
| --- | --- |
| `VLINE_BRIDGE_AUTHORIZE_URL` | `https://vline.online/api/integrations/tiktokhelper/authorize` |
| `VLINE_BRIDGE_TOKEN_URL` | `http://vline-bff:3211/api/integrations/tiktokhelper/token` с фактическим внутренним адресом BFF |
| `VLINE_BRIDGE_REDIRECT_URI` | `https://vline.online/tiktokhelper/auth/callback` |
| `VLINE_BRIDGE_CLIENT_ID` | Тот же идентификатор клиента, что в настройках кабинета |
| `secrets/tiktok_helper_client_secret` | Тот же серверный секрет, что в настройках кабинета |
| `VLINE_BRIDGE_ENTITLEMENT_URL` | Внутренний URL действующего `/entitlement` |
| `VLINE_BRIDGE_ENTITLEMENT_CLIENT_ID` | Идентификатор клиента действующей проверки подписки |
| `secrets/tiktok_helper_entitlement_client_secret` | Секрет клиента действующей проверки подписки |

Для обоих внутренних URL используйте HTTPS за пределами закрытой сети. Публикуйте исходный код сборки и передавайте её точный `SOURCE_REVISION`. Для первой установки применяются штатные миграции TikTokHelper. При переносе существующего проекта используйте его PostgreSQL, загруженные звуки и пакеты голосов после проверки резервной копии. Кэши старого домена браузер создаст заново на новом адресе.

## nginx и проверка

Подключите `deploy/nginx/tiktokhelper-http.conf` в `http {}` и `deploy/nginx/tiktokhelper-server.conf` в существующий HTTPS virtual host кабинета или его доверенный upstream. Объявите upstream `tiktok_helper_app` на loopback-порту пульта и `vline_cabinet_bff` по фактическому адресу BFF. Существующий `/api/` кабинета должен передавать `/api/site/links` в BFF. `proxy_pass` с завершающим `/` снимает префикс для HTTP и Socket.IO. Обмен кода и проверка сессии доступны только по внутреннему соединению. Проверьте, что внешний TLS-прокси тоже исключает строки запроса к `/api/integrations/tiktokhelper/authorize` и `/tiktokhelper/auth/callback` из журналов.

Перед переключением проверьте `docker compose -f compose.yaml -f deploy/cabinet.compose.yaml config --quiet` и `nginx -t`. В браузере проверьте прямой вход гостя, повторный вход в старое рабочее пространство, смену аккаунта и отзыв доступа. Затем проверьте чат, звуки и переход в кабинет во время эфира. Service worker пульта обслуживает `/tiktokhelper/` и обновляется после завершения эфира. Убедитесь, что `/api/site/links`, оба приватных маршрута BFF и cookie защищены через фактическую конфигурацию внешнего прокси.

Маршрутизация опирается на [публичный путь Vite](https://vite.dev/guide/build.html#public-base-path), [путь Socket.IO](https://socket.io/docs/v4/client-options/#path), [проксирование WebSocket в nginx](https://nginx.org/en/docs/http/websocket.html) и [RFC 9700 для OAuth](https://datatracker.ietf.org/doc/html/rfc9700#section-2.1).
